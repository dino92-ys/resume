# 유클리드소프트 — 기술 질문과 답변 초안

작성일: 2026-09-04. 질문은 공고와 제출본에서 추린 연습용 예상 질문이며, 회사의 실제 출제 정보가 아닙니다.

`문서 기반 답변`은 기본 문서에 기재된 경험입니다. `확인 필요` 항목은 과거에 수행한 것으로 단정하지 않습니다. `학습용 설명`은 일반 개념이며 실제 구현 여부와 구분합니다.

## 1. 개인 RAG 파이프라인은 어떻게 구성했나요?

**문서 기반 답변**

> ChromaDB와 bge-m3를 활용한 RAG 파이프라인을 FastAPI로 구성하고 Discord 봇에 연동했습니다. 검색 결과를 distance ≤ 0.45 조건으로 필터링했습니다.

**확인 필요**: 원천 문서, 청킹 방법, 임베딩 생성 시점, 컬렉션 설정, 검색 개수, 프롬프트 구성, 실제 생성 모델과 호출 경로. 스택 목록만 보고 Ollama가 모든 요청을 처리했다고 추정하지 않습니다.

**후속 질문**: 문서가 바뀌면 어떤 청크를 다시 임베딩하나요? 문서 삭제와 중복 등록은 어떻게 처리했나요?

근거: 개발자 프로필 대표 프로젝트 3.

## 2. 청킹과 임베딩 모델은 왜 그렇게 선택했나요?

**문서 기반 답변**: bge-m3 사용 사실은 확인됩니다. 청킹 설정과 모델 비교 근거는 확인 필요입니다.

**답변 완성 순서**: 문서 유형과 질문 특성, 청크 경계·크기·중첩, 모델 선택 이유, 비교한 설정, 검색 실패 사례를 채웁니다.

**학습용 설명**: 청크를 크게 만들면 더 많은 문맥을 담을 수 있지만 관련 없는 내용도 함께 검색될 수 있습니다. 작게 만들면 필요한 문맥이 여러 청크로 나뉠 수 있습니다. 문서 구조와 평가 질문을 기준으로 설정을 검증하는 이유를 설명합니다.

**후속 질문**: 표나 제목과 본문을 분리하면 어떤 문제가 생기나요? 모델을 바꾸면 기존 벡터와 인덱스는 어떻게 처리하나요?

## 3. 거리 임계값 0.45의 근거는 무엇인가요?

**문서 기반 답변**: distance ≤ 0.45 필터링은 기재되어 있습니다. 거리 척도와 선정 실험은 확인 필요입니다.

**확인할 자료**: 벡터 DB 설정, 검색 코드, 질문별 거리와 결과, 임계값을 바꾼 비교 기록.

**답변 틀**

> 거리 척도는 [확인 필요]였고, [확인 필요: 질문과 판정 기준]으로 결과를 확인했습니다. 임계값을 바꿨을 때 [확인 필요: 오답과 응답 거절 변화]를 보고 0.45를 선택했습니다.

괄호를 실제 근거로 채우기 전에는 완성된 답변으로 사용하지 않습니다. 단순 사례 확인이었다면 정량 평가를 수행한 것처럼 말하지 않습니다.

**후속 질문**: 임베딩 모델이나 거리 척도가 바뀌어도 0.45를 그대로 쓸 수 있나요? 관련 문서를 찾지 못하면 어떻게 응답했나요?

## 4. 검색 정확도와 응답 품질은 어떻게 평가했나요?

**문서 기반 답변**: 실무 POC의 검색 정확도 개선과 업무 대응 시간 단축 가능성 검증이 기재되어 있습니다. 평가 데이터·지표·전후 수치는 없습니다.

**확인 필요**: 평가 질문 작성자, 정답 근거 문서, 비교 기준, 수동 평가 여부, 실패 사례, 실험 기록.

**학습용 평가 구성 — 과거 수행 실적으로 사용하지 않음**

1. 질문별 필요한 근거 문서를 지정합니다.
2. 검색 결과에 필요한 근거가 들어왔는지 확인합니다.
3. 답변이 근거와 일치하고 질문에 답하는지 별도로 확인합니다.
4. 근거가 없는 질문에서 답변을 보류하는지 확인합니다.
5. 같은 질문·문서·모델 조건에서 변경 전후를 비교하고 지연시간도 기록합니다.

**후속 질문**: 검색은 맞았는데 답변이 틀리면 어디를 수정하나요? 검색 실패와 생성 실패를 어떻게 구분하나요?

## 5. 하이브리드 검색과 에이전트를 어떻게 구현했나요?

**문서 기반 답변**: Flowise AgentFlow 기반 하이브리드 검색 RAG를 설계·구현했습니다.

**확인 필요**: 결합한 검색 방식, 결과 결합 규칙, 흐름도, 도구 호출, 조건 분기, 대화 상태, 실패 시 처리, 직접 작성한 코드 범위.

**답변 기준**: 실제로 모델이 판단한 부분과 미리 정한 순서대로 실행한 부분을 분리합니다. AgentFlow라는 제품 이름으로 에이전트의 자율성을 설명하지 않습니다.

**후속 질문**: 도구 호출 결과가 틀리거나 실행에 실패하면 어떻게 처리하나요? 반복 호출이나 비용 증가를 어떻게 제한했나요?

근거: 경력기술서 2장. 구체적인 도구·평가 프레임워크는 아직 확인하지 않았습니다.

## 6. LoRA와 RAG를 함께 사용한 이유는 무엇인가요?

**문서 기반 답변**

> Bllossom-3B를 MLX 기반 LoRA로 파인튜닝했고 RAG를 병행했습니다. 제 프로젝트에서는 파인튜닝만으로 사실 정확도를 확보하는 데 한계가 있어 검색한 지식을 함께 활용했습니다.

**학습용 설명**: LoRA는 일부 추가 파라미터를 학습하는 파인튜닝 방법이고, RAG는 검색한 정보를 생성 시 입력에 제공하는 구성입니다. 두 방식이 어떤 문제를 해결했는지는 실제 학습 목적과 실험 결과로 설명합니다.

**확인 필요**: 학습 목적, 데이터 수와 출처, 학습·평가 분리, rank·학습률·epoch, 기준 모델과의 비교, RAG 병행 효과.

**후속 질문**: 프롬프트만 바꿔서는 해결되지 않았나요? 학습 데이터의 사실을 모델이 항상 정확히 답할 수 있나요?

근거: 이력서 AI/ML 프로젝트, 개발자 프로필 대표 프로젝트 3.

## 7. LLM 입력을 155배 줄인 과정을 설명해 주세요.

**문서 기반 답변 — STAR**

> 요약 단계에서 타임아웃과 HTTP 500이 반복됐습니다. 실제 입력을 확인하니 자재 마스터 12,336건을 대형 표에 부분 문자열로 매칭하면서 표 전체가 포함되고 있었습니다. 첨부에 자사 상호가 있는 경우 회사명으로 관련 내용을 선별하도록 바꿨습니다. HWPX 사례는 79,692자에서 514자로, PDF 사례는 64,026자에서 223자로 줄였고 문서에는 타임아웃 장애 해소를 기록했습니다.

**확인 필요**: 해당 사례의 입력·출력, 정보 누락 검증, 타임아웃 재발 여부를 확인한 기간. 모든 문서에 동일한 축소율이 적용된다고 말하지 않습니다.

**후속 질문**: 회사명이 없는 첨부는 어떻게 처리했나요? PDF의 표 구조는 어떻게 복원했나요? 입력을 줄여도 중요한 내용이 남았다는 근거는 무엇인가요?

근거: 경력기술서 1-3. PDF 처리에는 pypdf layout 모드를 사용했다고 기재되어 있습니다.

## 8. preview·rollback·commit은 어떻게 다른가요?

**문서 기반 답변**

> preview는 DB에 접속하지 않고 적재할 payload를 JSONL로 출력합니다. rollback은 실제 SQL을 실행한 뒤 롤백해 SQL 계약을 검증하고, commit은 행 단위로 커밋합니다. 세 모드가 같은 준비 객체를 공유하도록 구성했습니다. 잘못 적재된 경우를 위한 적재일 단위 삭제와 재처리 경로도 마련했습니다.

**설명할 한계**: 이미 커밋된 행은 뒤에서 발생한 롤백만으로 되돌아가지 않습니다. 행 단위 커밋을 선택한 이유, 부분 성공을 어떻게 확인하고 복구하는지 구분합니다.

**확인 필요**: 현재 중복 판별 기준, 재처리 상태 저장 방식, 동시 실행 처리. 이를 확인하기 전 정확히 한 번 처리(Exactly-once)를 보장했다고 말하지 않습니다.

**후속 질문**: LLM 호출 같은 DB 밖의 작업도 롤백되나요? 번호 충돌은 어떻게 막았나요?

근거: 경력기술서 1-4. 채번은 컬럼 직접 비교와 FOR UPDATE 잠금으로 전환했다고 기재되어 있습니다. 잠금이 보호하는 범위는 실제 코드 확인이 필요합니다.

## 9. 단위 테스트 71개로 무엇을 검증했나요?

**문서 기반 답변**

> 실제 DB나 네트워크 없이 가짜 DB 커서로 SQL 호출 순서·파라미터·트랜잭션 경계를 검증했습니다. 파일 확장자와 실제 형식이 다른 첨부 처리 같은 회귀 사례도 테스트로 고정했습니다.

**준비할 사례**: 적재 모드별 SQL·커밋 호출, HWP 확장자의 HWPX 파일 판별 중 직접 설명할 수 있는 테스트 2개를 선택합니다. 정확한 테스트명과 실패 전후 코드는 확인 필요입니다.

**설명할 한계**: 단위 테스트만으로 실제 DB 잠금, 외부 API, 운영 환경의 모든 동작을 검증했다고 말하지 않습니다.

**후속 질문**: 가짜 객체를 사용하면 놓치는 문제는 무엇인가요? 운영 배포 전에 어떤 추가 검증을 했나요?

근거: 경력기술서 1-2, 1-5.

## 10. DDL 자동 생성과 STRING 타입 통일을 설명해 주세요.

**문서 기반 답변**

> MSSQL과 Oracle의 시스템 카탈로그에서 컬럼·설명 정보를 추출하고 Python으로 Hive External Table DDL을 자동 생성했습니다. 2,000개 이상을 수동 작성 없이 처리했습니다. 이기종 타입 차이로 반복되던 로딩 오류는 컬럼을 STRING으로 통일하고 타입 변환을 분석 계층에 맡기는 방식으로 대응했습니다.

**학습용 검토**: 적재 경로는 단순해지지만 숫자·날짜의 타입 검증과 변환 책임이 후속 계층으로 이동합니다. 타입 오류를 없앤 것이 아니라 어디에서 처리하는지 설명해야 합니다.

**확인 필요**: 생성 건수의 기준, 생성 DDL과 원천 메타데이터 대조 방법, 잘못된 값의 후속 처리, 증분 적재 완료 여부.

**후속 질문**: 수정일시가 같은 행은 어떻게 처리하나요? 삭제와 늦게 도착한 데이터는 어떻게 처리하나요? 배치 실패 시 기준 시점은 언제 갱신하나요?

근거: 경력기술서 1-6. 증분 적재는 문서상 진행 중입니다.

**문서 기반 답변 범위**: Kaggle 프로젝트에서 피처 엔지니어링, 결측치 처리, 앙상블 비교, TF-IDF, CNN 설계를 수행했다고 기재되어 있습니다. 개별 프로젝트의 점수와 실험 조건은 확인 필요입니다.

**대표 프로젝트 답변 틀**

| :--- | :--- |
| 문제·목표값 | 확인 필요 |
| EDA에서 발견한 결측·분포·불균형 | 확인 필요 |
| 학습·검증·테스트 분리 방식 | 확인 필요 |
| 기준 모델과 선택 이유 | 확인 필요 |

**학습용 확인 질문**: 전처리 학습에 검증 데이터를 사용하면 왜 누수가 되나요? 과적합을 무엇으로 판단하나요? 정확도만으로 불균형 분류를 평가하면 어떤 문제가 있나요? 회귀와 분류에서 지표 선택은 어떻게 달라지나요?

## 12. 배포·협업·폐쇄망 환경 경험은 어디까지인가요?

**문서 기반 답변 범위**: FastAPI와 Discord 연동 배포, MLX·Ollama 사용, Windows·Rocky 실행 래퍼와 운영 환경 대응이 기재되어 있습니다.

**확인 필요**: Docker·Kubernetes 사용 여부, CI/CD 구성, PR·코드 리뷰 경험, 장애 대응 범위, 실제 폐쇄망 AI 배포 경험.

**답변 원칙**: 직접 구현한 배포 절차와 프레임워크 사용을 구분합니다. 로컬 실행을 대규모 서비스 운영이나 폐쇄망 구축으로 바꾸어 설명하지 않습니다.

**협업 사례 준비**: 누구에게 어떤 문서를 전달했는지, 기술적 선택을 어떻게 설명했는지, 피드백으로 무엇을 바꿨는지 한 사례를 기록합니다.

## 13. 확인이 필요한 답변을 보완하는 순서

1. 실제 코드·설정·노트에서 사실을 확인합니다.
2. 측정했다면 조건과 결과를 적고, 측정하지 않았다면 사용한 관찰 방법만 적습니다.
3. 과거의 한계와 앞으로 적용할 검증 방법을 별도 문장으로 구분합니다.
4. 답변마다 “본인 행동”과 “확인한 결과”가 있는지 점검합니다.
