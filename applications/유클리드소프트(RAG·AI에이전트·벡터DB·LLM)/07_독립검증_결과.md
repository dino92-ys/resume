### L2. rollback은 preview의 하위 모드입니다

`03:103`이 세 모드를 대등하게 서술하나, 코드상 구조는 다릅니다.

- `db_ingest_final_direct.py:30` "`--rollback` 옵션은 반드시 `--preview`와 함께 사용해야 합니다."
- `:20` 기본 실행 — 키워드 조회 → payload 준비 → INSERT → 행별 commit
- `:23` `--preview` — 결과 파일(JSONL)만 추출
- `:27` `--rollback --preview` — INSERT 실행 후 행별 rollback

`:280`의 `[WHY] preview, rollback-preview, 실제 INSERT가 서로 다른 변환 경로를 사용해
결과가 달라지는 것을 막기 위함이다`는 `03:103`의 "같은 준비 객체를 공유" 서술과 정확히 일치합니다.

### L3. LoRA scale/dropout 충돌의 원인을 특정할 수 있습니다 (추정)

`lora_config.yaml:23-26`:

```yaml
lora_parameters:
rank: 8
scale: 16.0
dropout: 0.05
```

`lora_parameters:` 하위 키가 **들여쓰기되지 않아** YAML 파싱 시 최상위 키가 됩니다.
그 결과 `adapter_config.json`에는 최상위에 `"scale": 16.0`, `"dropout": 0.05`가 기록되고,
실제 LoRA에 전달되는 `"lora_parameters"`는 `{"rank": 8, "dropout": 0.0, "scale": 20.0}`
(MLX 기본값)로 남았습니다.

**추정**: 실제 적용값은 `scale 20.0`, `dropout 0.0`, `rank 8`일 가능성이 높습니다.
MLX 버전별 파싱 동작 확인이 필요하므로 `확인` 등급으로 둡니다.
`05` 3-4의 "학습 당시 실제 scale·dropout" 항목을 채울 때 이 구조를 근거로 쓸 수 있습니다.

### L4. train.jsonl 1,672건 표기는 정확합니다

`wc -l`은 1671을 반환하지만 마지막 줄에 개행이 없습니다.

## 7. 셀프 리플렉션 — 이번 검증에서 조심한 부분

- **`wc -l` 1671을 그대로 쓸 뻔했습니다.** `train.jsonl`의 마지막 줄에 개행이 없어
  줄 수와 레코드 수가 달랐습니다. 바이트 단위로 다시 세어 1,672건을 확인했습니다.
  문서 표기가 맞고 제 첫 계산이 틀렸습니다.

- **ChromaDB의 46건을 JSON 파일만 보고 판단할 뻔했습니다.** `chroma.sqlite3`의 embeddings를
  직접 조회해 46건을 확인한 뒤에야 `실행` 등급을 부여했습니다.
  JSON만 있었다면 `코드` 등급이 맞습니다.

- **LoRA scale 충돌의 원인(L3)은 추정입니다.** YAML 들여쓰기 누락이라는 구조는 파일에서 확인했지만,
  MLX가 실제로 어느 값을 적용했는지는 학습 로그가 없어 확정할 수 없습니다.
  "실제 적용값은 20.0"이라고 단정하지 않고 `확인` 등급으로 남겼습니다.

- **H2를 "제출본이 허위"라고 쓸 뻔했습니다.** 설계 문서가 실무 POC와 다른 프로젝트일 수 있으므로
  (H1), 설계 문서의 내용만으로 제출본을 반증할 수 없습니다.
  "현재 자료로 코드 확정 불가"까지만 적었습니다.

- **Titanic 생존율 38%는 검증하지 못했습니다.** `pandas` 미설치로 재계산에 실패했고,
  노트북 저장 출력에도 해당 값이 없어 `검증 불가`로 남겼습니다.
  일반적으로 알려진 수치와 일치한다는 이유로 통과시키지 않았습니다.
