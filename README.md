### 문서 사이의 관계

- **포트폴리오는 파생 문서입니다.** 경력기술서·개발자프로필·이력서에 이미 있는 사실만 고르고 재구성합니다.
  새 수치·새 경험·새 판단 이유를 포트폴리오에서 처음 쓰지 않습니다.
- 같은 성과는 모든 문서에서 **같은 표기**를 씁니다. 대표 수치 표기는 AGENTS.md §3을 따릅니다.
- 고객사 내부 테이블명 같은 식별자는 설명으로 바꿔 씁니다(예: "AI 요약 결과 테이블"). 이메일은 공개본에도 넣습니다.
- 담당 범위는 기준 문서의 서술을 그대로 옮깁니다. "하지 않은 것"을 부정형으로 덧붙이지 않습니다.
- 면접 대비 문서 `01_포트폴리오_발표_대본.md`·`02_프로젝트별_기술해설과_예상질문.md`는 제출 문서가 아니며,
  위 문서를 근거로 작성합니다(AGENTS.md §9).

### 포트폴리오 구성 기준

| 순서 | 프로젝트 | 근거 문서 |

| 2 | RAG 기반 사내 지식 검색 파이프라인 PoC | 경력기술서 2장, 개발자프로필 프로젝트 2 |
| 3 | 위니쿠키 AI 챗봇 | 개발자프로필 프로젝트 3, 이력서 개인 프로젝트 |
| 4 | Kaggle 머신러닝 프로젝트 | 개발자프로필 프로젝트 4, 이력서 개인 프로젝트 |

- 순서는 개발자프로필의 대표 프로젝트 순서를 따릅니다.
- 포트폴리오는 요약과 핵심 수치만 두고, 과제·수행 내용·성과의 상세는 경력기술서 해당 절을 가리킵니다(같은 문장을 두 문서에 반복하지 않음).
- 원본 문장을 재구성할 때 원본의 과제·해결·성과 묶음을 바꾸지 않습니다. 다른 절의 항목을 한 과제의 해결책으로 엮지 않습니다.
- 구조도는 기존 문서에 있는 것만 씁니다(현재 프로젝트 1의 구조도 1개).
- 한계·실패 사례는 기본 문서에 근거가 있는 것만 씁니다(예: 증분 적재 진행 중, PoC 단계).

## 2. 버전 규칙

- 5개 문서는 **항상 같은 버전 번호**를 씁니다. 한 문서만 고쳐도 다섯 개를 함께 올려, 같은 버전끼리 한 세트로 이해할 수 있게 합니다.
- 이전 버전은 파일로 남기지 않고 git 이력으로 관리합니다. 파일명 변경은 `git mv`로 해서 이력을 잇습니다.
- PDF는 md에서 만드는 산출물이며 git으로 추적하지 않습니다(`.gitignore`). 제출 전 해당 버전으로 다시 만듭니다.

## 3. 수정 절차

1. **기준 문서 확인** — 가장 최근에 사용자가 고친 문서를 기준으로 삼습니다. 이전 문서와 다른 부분은 의도된 변경으로 보고, 이유가 불분명하면 먼저 묻습니다.
2. **사실 변경** — 경력·수치·담당 범위가 바뀌면 기준 문서의 표현을 나머지 문서 전체에 같은 표기로 반영합니다.
3. **수치는 계산해서 바꾸지 않습니다** — 경력 기간 같은 값은 문서에 있는 값을 유지하고, 갱신이 필요하면 계산 방식을 확인받은 뒤 바꿉니다.
4. **버전 일괄 변경** — §2 규칙대로 5개 문서를 같은 버전으로 올리고, AGENTS.md §4 파일 목록과 01·02의 링크를 함께 고칩니다.
5. **지침 사본 갱신** — AGENTS.md를 고쳤다면 `python docs/build_prompt.py`로 `docs/PROMPT.md`를 다시 만듭니다.
6. 회사별 조정은 루트 문서가 아니라 `applications/` 아래 파생본에서 합니다.
